# Tool Design & MCP Integration

### 1. Problem statement

In enterprise Claude agent deployments, tool misselection, unhandled execution failures, and context overload frequently cause agent failure. Vague tool descriptions cause models to select incorrect tools during ambiguous requests, while opaque error messages like "Operation failed" prevent intelligent error recovery. Furthermore, overloading agents with too many tools (>4–5 tools) degrades model reasoning, and improper Model Context Protocol (MCP) server configuration risks exposing secrets or creating inconsistent developer environments.

### 2. Summary

The [Tool Design & MCP Integration](https://pods.vizuara.ai/courses/claude-certified-architect/tool-design-mcp/article) lesson provides a framework for building production-grade tools and configuring MCP servers:

* **Tool Descriptions as Selection Mechanisms**: Tool descriptions serve as the model's primary selection signal. Descriptions must address five core elements: specific utility, input schema/constraints, expected output structure, explicit positive use cases, and negative boundary conditions (when *not* to use). Overlapping generic tools should be split or renamed, and system prompts must avoid keyword traps that unintentionally bias tool selection.
* **Structured Error Handling**: Tool failures must leverage the MCP `isError: true` flag accompanied by structured metadata JSON containing `errorCategory`, `isRetryable`, `errorCode`, and `customerMessage`. Failures fall into four categories: **Transient** (retryable), **Validation** (input fix required), **Business** (policy violation, non-retryable), and **Permission** (requires escalation). Distinguish between valid empty results (e.g., 0 records found) and actual system access failures.
* **Tool Distribution & Control**: Restrict each agent to **4–5 tools max** by scoping tool access to specific subagent roles (e.g., Triage vs Billing vs Order Specialist). Control model execution using `tool_choice` settings: `"auto"` (standard), `"any"` (forces tool invocation), or explicit tool forcing `{"type": "tool", "name": "..."}` for sequential orchestration.
* **MCP Configuration Architecture**: Use project-level `.mcp.json` files for shared team tooling with environment variable expansion (`${TOKEN}`) to avoid committing secrets. Reserve user-level `~/.claude.json` for local/personal tools. Leverage MCP Resources for read-only catalog browsing without tool call overhead.
* **Built-in Tool Usage & Incremental Exploration**: Utilize Claude's built-in tools efficiently: **Grep** (content search), **Glob** (file path matching), **Read/Write** (full file operations), and **Edit** (targeted replacements with unique text anchors). If `Edit` fails due to non-unique anchor text, fall back to `Read` + `Write`. Conduct codebase investigations incrementally via a **Grep → Read → Trace** flow.

## Code Snippets & Explanations

#### 1. Forced Tool Selection via `tool_choice`

```python
# Turn 1: Force metadata extraction before any processing
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    tools=tools,
    tool_choice={"type": "tool", "name": "extract_metadata"},
    messages=messages
)

# Append results to message history...
messages.append({"role": "assistant", "content": response.content})
messages.append({"role": "user", "content": [{
    "type": "tool_result", 
    "tool_use_id": response.content[0].id, 
    "content": "Metadata extracted"
}]})

# Subsequent Turns: Allow autonomous model selection
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    tools=tools,
    tool_choice={"type": "auto"},
    messages=messages
)

```

*Explanation:* Demonstrates how setting `tool_choice` to a specific tool guarantees execution order on turn 1 before returning control to `"auto"` for downstream steps.

#### 2. Project-Level MCP Server Configuration (`.mcp.json`)

```json
{
  "mcpServers": {
    "jira": {
      "command": "npx",
      "args": ["@anthropic/jira-mcp-server"],
      "env": {
        "JIRA_URL": "https://yourcompany.atlassian.net",
        "JIRA_TOKEN": "${JIRA_TOKEN}"
      }
    }
  }
}

```

*Explanation:* Configures a shared team MCP server at the project root while safely extracting actual credentials from developer environment variables via `${JIRA_TOKEN}` expansion.

#### 3. Structured Error Response Metadata

```json
{
  "isError": true,
  "content": "Refund denied: return window expired (90 days)",
  "metadata": {
    "errorCategory": "business",
    "isRetryable": false,
    "errorCode": "RETURN_WINDOW_EXPIRED",
    "customerMessage": "Unfortunately, this order is past the 90-day return window and is no longer eligible for a refund."
  }
}

```

*Explanation:* Returns actionable error metadata allowing Claude to recognize the non-retryable business failure immediately and convey a pre-approved explanation to the user.

### 3. Clear & Simple Explanation

Designing tools for Claude is similar to managing a specialized workplace team:

* **Tool Descriptions as Job Postings**: If two job descriptions both say "handles paperwork," employees will route tasks randomly. Adding specific duties, boundaries, and negative rules ensures every request reaches the correct person.
* **Structured Errors as Diagnostic Reports**: A car dashboard warning light that says "Error" forces a driver to guess. A dashboard displaying "Low Tire Pressure (20 PSI) – Non-critical, drive slowly to service station" tells the driver exactly how to react.
* **Scoped Tool Sets**: Giving one employee 18 complex tools causes confusion and decision paralysis. Assigning 3–4 specialized tools per person keeps decisions fast and accurate.
* **Incremental Code Search**: When investigating a issue in a library, you don't read every book in the library cover-to-cover. You use the index (**Grep**), open the exact chapter (**Read**), and follow references (**Trace**).

### 4. Real-World Application

**Scenario: Enterprise Customer Service & Billing Platform**
An e-commerce system uses a coordinator agent to route customer requests to specialized role-based subagents integrated with internal database services via MCP.

```
                         [User Request]
                               │
                               ▼
                    [Triage Agent (3 Tools)]
                    (get_customer, route_to_spec)
                               │
                ┌──────────────┴──────────────┐
                ▼                             ▼
   [Order Specialist (4 Tools)]   [Billing Specialist (4 Tools)]
   (lookup_order, track_shipment) (process_refund, get_invoice)
                │                             │
                ▼                             ▼
       [MCP Server: DB]               [MCP Server: Payment]
                │                             │
       (Returns ISO Data)            (Returns isError: true)
                                              │
                                              ▼
                                 [Structured Error Metadata]
                                 (errorCategory: business)
                                              │
                                              ▼
                                 [Pre-written User Message]

```

1. **Routing & Scoping**: The Triage Agent inspects the user query using 3 focused tools, routing refund claims to the Billing Specialist without exposure to shipping tools.
2. **Safe MCP Configuration**: Payment tools run via a `.mcp.json` server with API keys loaded safely via `${PAYMENT_KEY}` environment variables.
3. **Structured Recovery**: If a refund exceeds policy limits, the payment service returns `isError: true` with `errorCategory: "business"` and `isRetryable: false`. The agent avoids retrying and outputs the pre-formatted `customerMessage`.

### 5. Key Terms Note Section

### Key Technical Terms

* **Primary Selection Signal**: The combination of tool name, description, and input schema that Claude evaluates to match user intent to a tool.
* **Negative Boundaries**: Explicit "Do NOT use for..." instructions in a tool description that prevent misselection across overlapping tools.
* **System Prompt Keyword Trap**: A failure state where generic verbs in system prompts (e.g., "analyze") trigger unintended bias toward tools containing matching words.
* **`isError` Flag**: An MCP protocol boolean flag indicating that a tool call resulted in an execution failure rather than standard data output.
* **Transient Error**: A temporary system failure (e.g., timeout, rate limit) where `isRetryable` is set to `true`.
* **Business Error**: A policy violation (e.g., return window expired) where `isRetryable` is set to `false`.
* **Validation Error**: An input formatting failure requiring parameter adjustment before re-invocation.
* **Permission Error**: An authorization boundary failure requiring escalation to elevated agents or human operators.
* **Scoped Tool Access**: Restricting an agent's available tools to 4–5 role-specific operations to maximize selection accuracy.
* **`tool_choice`**: An API configuration parameter (`"auto"`, `"any"`, or explicit tool name) controlling model tool execution enforcement.
* **Project-Level Config (`.mcp.json`)**: A version-controlled JSON configuration defining shared MCP tools with environment variable expansion.
* **MCP Resources**: Read-only data endpoints exposed by MCP servers that enable agents to inspect catalogs without executing tool calls.
* **Grep → Read → Trace**: The recommended incremental codebase exploration pattern that prevents context window flooding.

5. While analyzing a codebase, Claude attempts to use the built-in `Edit` tool to update a function call, but the tool invocation fails because the target anchor text appears in multiple places in the file. What is the recommended fallback pattern?

* A) Use `Glob` to delete duplicate files before retrying `Edit`.
* B) Force tool execution using `tool_choice: "any"`.
* C) Switch to `Read` to inspect the full file and surrounding context, then apply changes using `Write`.
* D) Execute `Grep` repeatedly until the non-unique text disappears.

---

--- **Answer Key & Explanations** ---

1. **B** - The system prompt's use of the verb "Analyze" matches the word "analyze" in `analyze_content`, creating a system prompt keyword trap that overrides tool descriptions. To fix this, system prompts should use task-oriented language rather than verbs matching tool names.
2. **C** - Errors with `isRetryable: false` and `errorCategory: "business"` represent strict policy violations (such as expired return windows). Retrying will yield the same failure and waste context tokens; the agent should accept the rule and present the pre-formatted explanation to the user.
3. **A** - Project-level `.mcp.json` files are committed to version control so all team members share the configuration, while environment variable expansion (e.g., `"${JIRA_TOKEN}"`) keeps sensitive access tokens out of the repository.
4. **D** - Specifying `tool_choice: {"type": "tool", "name": "extract_metadata"}` explicitly forces the model to call `extract_metadata` on the first turn. Switching to `"auto"` on subsequent turns restores standard autonomous tool selection.
5. **C** - The `Edit` tool requires unique anchor text to perform surgical string replacements. When anchor text is ambiguous or non-unique, the correct fallback is reading the entire file via `Read`, determining the target location via surrounding context, and updating via `Write`.
