# [Claude Code Configuration & Workflows](https://pods.vizuara.ai/courses/claude-certified-architect/claude-code-workflows/article)

### 1. Problem statement

When developers open Claude Code in an enterprise codebase without dedicated configuration, the model generates generic, unaligned code. It defaults to standard library assumptions (e.g., Express instead of Fastify, Jest instead of Vitest, incorrect directory paths, and missing required error-handling middleware). Without explicit project rules, individual developers receive inconsistent results, leading to manual refactoring, broken architectural boundaries, and non-compliant code generation.

### 2. Summary

The [Claude Code Configuration & Workflows](https://pods.vizuara.ai/courses/claude-certified-architect/claude-code-workflows/article) lesson details how to transform Claude Code into a team-aligned tool through layered configurations, custom commands, execution strategies, and automated CI/CD pipelines.

* **CLAUDE.md Configuration Hierarchy**:
  * **Level 1: User-level (`~/.claude/CLAUDE.md`)**: Contains personal preferences (editor shortcuts, preferred comment style). This file is **never checked into version control** and remains local.
  * **Level 2: Project-level (`.claude/CLAUDE.md` or `CLAUDE.md` in root)**: Shared team conventions (frameworks, naming standards, testing tools) checked into version control.
  * **Level 3: Directory-level (`CLAUDE.md` in subdirectories)**: Rules specific to subtrees (e.g., `src/api/` vs `src/frontend/`).
* **Precedence Rule**: Most specific level wins (**Directory > Project > User**).
* **Inspection**: The `/memory` command reveals all loaded configuration files.
* **Modular Structure**: Large configurations can be split using `@import ./claude/rules/feature.md`.


* **Path-Specific Rules (`.claude/rules/`)**:
  * Uses YAML frontmatter with `paths` glob patterns (e.g., `**/*.test.tsx`, `terraform/**/*`).
  * Differs from Directory-level `CLAUDE.md` by applying rules across non-contiguous directory structures based on file extension or path patterns.


* **Custom Slash Commands vs. Skills**:
* **Slash Commands (`.claude/commands/`)**: Reusable prompt templates utilizing the `$ARGUMENTS` placeholder for parameters.
* **Skills (`.claude/skills/`)**: Extended commands configured via `SKILL.md` frontmatter.
  * **`context: fork`**: Executes the skill in an isolated sub-agent context window, returning only the final output to keep the main conversation window clean.
  * **`allowed-tools`**: Restricts sub-agent capabilities based on least privilege.


* **Execution Strategies**:
  * **Plan Mode**: Essential for multi-file changes (10+ files), open-ended refactoring, or architectural decisions.
  * **Direct Execution**: Best for clear, scoped fixes, single-function edits, or bug fixes with known root causes.
  * **Explore Subagent**: Executes preliminary investigation in a separate context window prior to choosing an execution path (**Explore → Decide → Execute**).


* **Iterative Refinement & CI/CD**:
* **Refinement Patterns**: Uses Concrete I/O Examples, Test-Driven Iteration, The Interview Pattern (forcing Claude to ask clarifying questions first), and Batching Interacting Issues.
* **Non-Interactive CI/CD**: Uses the `-p` (`--print`) flag to prevent pipeline hanging.
* **Structured JSON Output**: Pairs `--output-format json` with `--json-schema` to enforce strict response validation for PR checks.
* **Session Context Isolation**: Ensures pull request reviews execute in a fresh, isolated session to eliminate self-review bias.



#### Workflows & Capabilities Comparison

| Feature / Concept | Scope & Location | Execution Context | Primary Exam Use Case |
| --- | --- | --- | --- |
| **User CLAUDE.md** | `~/.claude/CLAUDE.md` | Main Session | Personal preferences, local shortcuts (Never share in git). |
| **Project CLAUDE.md** | `.claude/CLAUDE.md` | Main Session | Core project conventions, testing frameworks, coding standards. |

| **CI/CD Review** | CLI execution (`claude -p`) | Isolated Non-Interactive Session | Automated, unbiased PR review returning structured JSON. |

## Code Snippets & Explanations

#### 1. Path-Specific Rule with Glob Patterns (`.claude/rules/testing.md`)

```yaml
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
  - "**/*.spec.ts"
---

## Testing Conventions

- Use `describe` blocks to group related tests
- Use `it` for individual test cases (not `test`)
- Mock external services with `vi.mock()`, never real network calls
- Use `screen.getByRole` over `getByTestId` for accessibility

```

*Explanation:* Uses YAML frontmatter to conditionally load testing guidelines only when Claude Code edits files matching specified glob patterns, preventing rule pollution during non-test edits.

#### 2. Isolated Context Skill Definition (`.claude/skills/migration/SKILL.md`)

```yaml
---
context: fork
allowed-tools:
  - read
  - write
  - bash
argument-hint: "migration name (e.g., add-user-preferences-table)"
---

# Generate Database Migration
Create a new database migration with the given name:
1. Create migration file at `migrations/{timestamp}_{$ARGUMENTS}.sql`
2. Include UP and DOWN sections
3. Follow column naming conventions in .claude/rules/database.md
4. Add a corresponding test in `migrations/tests/`

```

*Explanation:* The `context: fork` header spawns a separate sub-agent to execute file creations and bash commands, protecting the main developer session from context window bloat.

#### 3. Non-Interactive CI/CD PR Review Command

```bash
claude -p "Review this PR for security vulnerabilities" \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "issues": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "file": { "type": "string" },
            "line": { "type": "integer" },
            "severity": { "type": "string", "enum": ["critical", "warning", "info"] },
            "description": { "type": "string" }
          },
          "required": ["file", "line", "severity", "description"]
        }
      },
      "approve": { "type": "boolean" }
    },
    "required": ["issues", "approve"]
  }'

```

*Explanation:* Executes Claude Code non-interactively (`-p`) inside a CI/CD runner, enforcing a strict JSON schema that automated build pipelines can validate to approve or block merges.

### 3. Clear & Simple Explanation

Managing Claude Code configuration is like setting up guidelines for a software development team:

* **CLAUDE.md Hierarchy**: User-level rules are your personal desk setup; Project-level rules are the corporate handbook; Directory-level rules are team-specific project boards. If a conflict arises, the local team rules always win over corporate and personal setups.
* **Path-Specific Rules**: Instead of placing rules in every directory, path rules act like tagged rulebooks that open only when a developer works on specific file types (such as test suites or Terraform files).
* **Commands vs. Skills**: Commands are like quick macros typed into your terminal. Skills are subroutines that run in a separate workspace (`context: fork`), completing heavy background tasks and returning only the final report.
* **Plan Mode vs. Direct Execution**: Plan Mode is architectural blueprinting before construction. Direct Execution is replacing a single lightbulb.
* **CI/CD Integration**: Running `-p` with `--json-schema` is like assigning an automated, unbiased robot inspector to check code diffs in a separate room and output a standardized scorecard.

### 4. Real-World Application

**Scenario: Automated Monorepo CI/CD & Migration Pipeline**
A financial enterprise monorepo requires strict separation between frontend React applications, backend Fastify microservices, and database migrations, enforced via automated CI/CD checks.

```
                          [Developer Git Push]
                                   │
                                   ▼
                       [GitHub Actions Runner]
                                   │
      ┌────────────────────────────┴────────────────────────────┐
      ▼                                                         ▼
[Fresh Session Execution]                             [PR Review Task]
(claude -p --output-format json)                     (Isolated Context)
      │                                                         │
      ├──────────────────────────┐                              │
      ▼                          ▼                              ▼
[Loads Project CLAUDE.md] [Evaluates Diff]             [Schema Enforcement]
(.claude/rules/api.md)    (Isolated Session)           (--json-schema)
      │                          │                              │
      └──────────────────────────┴──────────────┬───────────────┘
                                                │
                                                ▼
                                    [JSON Quality Scorecard]
                                    (issues[], approve: bool)
                                                │
                                    ┌───────────┴───────────┐
                                    ▼                       ▼
                             [approve: true]        [approve: false]
                                    │                       │
                                    ▼                       ▼
                              [Merge PR]              [Block Merge]

```

1. **Local Authoring**: Developers use slash commands (`/new-api-endpoint`) that reference project standards defined in `.claude/CLAUDE.md`.
2. **Path Rules Trigger**: Editing `migrations/*.sql` automatically enforces database conventions from `.claude/rules/database.md`.
3. **CI Pipeline Execution**: Upon opening a Pull Request, GitHub Actions invokes `claude -p` in a fresh, isolated session.
4. **Structured Decision**: The runner validates the JSON response against `--json-schema` to post inline code comments and determine merge approval.

### 5. Key Terms Note Section

### Key Technical Terms

* **`CLAUDE.md` Hierarchy**: The 3-tier precedence structure (Directory > Project > User) governing how system instructions are loaded into Claude Code.
* **Precedence Rule**: The resolution order where the most specific configuration scope overrides broader global instructions.
* **`@import` Syntax**: The modular inclusion directive used to break monolith `CLAUDE.md` files into smaller rule files.
* **`/memory` Command**: The CLI diagnostic command used to inspect loaded `CLAUDE.md` files and active memory state.
* **Path-Specific Rules**: Rules in `.claude/rules/` that trigger based on glob matching defined in YAML frontmatter.
* **`$ARGUMENTS`**: The parameter placeholder variable inside slash commands replaced by user input.
* **`context: fork`**: A skill configuration setting that executes sub-tasks inside an isolated context window.
* **Plan Mode**: A reasoning-first execution state used for complex, multi-file architectural changes.
* **Explore Subagent**: A decoupled discovery sub-agent pattern used to investigate codebases without polluting the main session history.
* **The Interview Pattern**: A prompting strategy that forces Claude to ask clarifying questions prior to generating implementations.
* **Non-Interactive Mode (`-p` / `--print`)**: The CLI flag that enables headless, unattended execution in script environments.
* **`--json-schema`**: The CLI argument that enforces strict structural validation on model outputs.
* **Session Context Isolation**: The practice of executing code reviews in a fresh, independent session to prevent self-review bias.

5. When multiple configuration files exist in a project, which statement correctly describes the precedence rule when editing a file in `src/api/v2/users.ts`?

* A) Directory-level rules override Project-level rules, which override User-level rules.
* B) User-level `~/.claude/CLAUDE.md` overrides all other levels because it represents developer preferences.
* C) Project-level `.claude/CLAUDE.md` overrides Directory-level rules unless `@import` is used.
* D) Rules defined in `.claude/commands/` override all `CLAUDE.md` hierarchy levels unconditionally.

---

--- **Answer Key & Explanations** ---

1. **A** - **In `.claude/rules/testing.md` using YAML frontmatter with a `paths` field containing glob patterns.** Path-specific rules in `.claude/rules/` use YAML frontmatter with `paths` globs to activate cross-cutting rules across non-contiguous directories. Option B is unmaintainable; Option C affects only the local machine and is not checked into git; Option D incorrectly applies sub-agent context to basic rules.
2. **C** - **As a custom Skill defined in `.claude/skills/migration/SKILL.md` configured with `context: fork` in its frontmatter.** The `context: fork` setting runs the skill in an isolated sub-agent context window, returning only the final result to keep the primary conversation context clean. Options A and B execute within the main context window; Option D is used for automated CI execution.
3. **D** - **`claude -p "Review PR" --output-format json --json-schema '<schema>'` executed in a fresh, isolated session.** Running in non-interactive mode (`-p`) with `--output-format json` and `--json-schema` provides validated, machine-readable JSON. Running in a fresh session eliminates self-review bias. Options A, B, and C fail to enforce schema validation or isolate review sessions.
4. **B** - **Use Plan Mode first to explore the codebase, evaluate tradeoffs, and present a plan for approval before making changes.** Plan mode is recommended for changes spanning many files (10+), ambiguous scopes, or multi-approach architectural decisions. Option C risks mid-refactor failure; Options A and D force rigid, unvalidated changes across the repository.
5. **A** - **Directory-level rules override Project-level rules, which override User-level rules.** The precedence order follows "most specific wins" (Directory > Project > User). Option B is incorrect because user-level is global and least specific; Option C reverses project and directory precedence; Option D confuses action templates with system rules.
